# 已确认的前端重构设计

2026-11-01：用户认可交互预览的 UI、样式、主题颜色，要求保留当前全部功能，按步骤开发并在每一步完成后推送。

## 正式方向

- 使用“优选工作台”：桌面侧边导航，任务参数与结果并行展示，全局任务状态；移动端重排导航、参数和结果。
- “分步优选”只是对比方案，不作为第二套产品实现。不维护两套 UI 或两套业务状态。
- 保留预览蓝色主操作、冷灰蓝背景、清晰内容表面、细分割线、浅/深/自动主题；采用本地字体，发布包不依赖字体 CDN。
- 密集数据允许紧凑显示；移动端需要完整显示关键值和动作。圆角保持克制，功能优先于装饰。
- 预览示例数据不进入生产界面。未迁移能力明确提示并链接旧版，不展示假的连接、任务、发布成功状态。

## 全量功能与技术边界

- [功能总览](README.md)中 112 项当前能力/兼容约束是迁移下限；每个模块文档用于对照验收，不以预览展示为上限。
- 后端 Go 扫描/测速算法、CLI 和现有 WebSocket 类型保持兼容。只为静态资源、确有需要的配置/发布能力增加后端调整。
- 原生 ES modules、独立 CSS、Go embed；首轮不引入 UI 框架或必须运行的 Node 构建服务。Node 内置测试用于纯逻辑；浏览器测试用于交互/可达性。
- 不继续把 HTML/CSS/JS 全写在 index.html；按 [架构原则](architecture.md)划分模块，每个领域迁移真实数据/状态/视图一起验收。
- 改动仅在 `frontend/rebuild`；不改 `.github/`，不改根目录参考 Go 源码，不改独立 Worker 仓库。

## 发布配置

- 统一管理已保存目标，执行时选择目标；GitHub、edgetunnel 各自保留平台动作。参见 [发布模块](modules/publishing.md)。
- 第一轮迁移保持浏览器存储并兼容旧账户；不以“统一管理”为由隐含改成跨设备服务端密钥库。
- Web/CLI/后台共用持久化配置及页面关闭后的可靠自动推送需要用户确认存储和凭据范围，再单独计划。
- DNS 接入尚未指定管理商；本轮不实现空插件或伪装已接入。增加首个管理商时另做平台计划和 mock API 测试。

## 分阶段发布

- 第一阶段新工作台位于 `/workbench`，旧默认 `/` 不变；途中保留完整旧功能的可用入口。
- 未迁移模块不混用旧 DOM，不把旧整页嵌进新工作台伪装重构完成。
- 后续完成所有功能、认证、Android 适配和回归后，新工作台切换为 `/`，旧版明确留在 `/legacy` 供过渡；旧版清理另行决定。
- 每个阶段执行测试、审查、Go 测试/静态检查、Linux amd64 测试构建后再提交并推送；失败的阶段不带着失败结果推送或进入下一阶段。
- 推送只到配置的 Git 远端 `origin` 的 `frontend/rebuild`，不合并主分支、不强推、不自动创建 PR。

## 仍需确认而不阻塞基础迁移的事项

- 是否增加服务端发布目标库供 Web/CLI/后台共用。
- 首个 DNS 平台、单/多条记录更新及旧记录清理规则。
- Android 真机/SDK 可用性；代码级适配不能代替最终 APK 验收。
